# How big does the DB-BOA surrogate have to be?

_Auto-generated by `experiments/objective_noise_audit.py --knee`._

OBJ-13 decided to **measure** the surrogate size rather than pick one: sweep `surrogate_rows` and report the curve, so the choice is defensible rather than arbitrary. Measured in `legacy` mode (`draws=25`, seed 42) — `deterministic` reports a std of 0 by construction, which says nothing about whether the one draw it freezes is a good one.

`noise_to_signal` = 2·std ÷ config-to-config range. **Below 1 means a single evaluation can separate two candidates**; at or above 1 the search is ranking draws, not models.

> ⚠ **The 2,000-row cell here is not the same measurement as the 2,000-row headline in `OBJECTIVE_noise_audit.md`, and should not be quoted as a reproduction of it.** Every size below draws from one fixed 40,000-row pool — held constant precisely so that surrogate size is the only thing moving across the rows of this table — whereas the main audit draws from `_eval_subset`'s default 6,000. Different pool, different subsample, different number. The table is internally comparable; it is not cross-comparable with the audit.

> The pool is also **40,000 rows against a largest surrogate of 20,000**, so it is never the binding constraint. That matters: `_eval_subset` defaults to 6,000, and at that default every point above 6,000 would have silently received ~6,000 rows and the curve would have gone flat for a reason that has nothing to do with a knee. `surrogate_rows_achieved` is recorded per cell so the claim is checkable rather than trusted.

## Scoring pre-registration 6 — does the fraud floor drive the noise?

`n_f = max(30, rows x fraud_rate)`, so the `_MIN_FRAUD_ROWS = 30` floor stops binding at very different sizes on the two datasets. **Pre-registered:** BankSim's `noise_to_signal` improves markedly with size while ULB's barely moves until the top of the grid — and *if ULB improves anyway, the fraud count is not the driver* and the "n≈9 positives" mechanism is wrong.

## Reading the k columns

The `k=3` and `k=5` columns are **not** separate runs: the mean of k independent draws has std ÷ √k, so they follow from the measured std at zero extra CPU. They say how far `averaged` mode gets on the same surrogate size, and are the honest way to compare 'more rows' against 'more draws' — the two knobs cost the same currency.
