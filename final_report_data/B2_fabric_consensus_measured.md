- **Peak sustained throughput: 40.3 tps** @ concurrency 10.
- **Clean region (concurrency 1→10):** 0 failures, throughput rises ~80× (0.5→40 tps). At low concurrency each txn pays the full 2 s BatchTimeout; as more txns arrive within one timeout window the orderer batches them into a single block, amortising the timeout — the classic Fabric latency/throughput trade-off, here measured not assumed.
- **MVCC knee (concurrency > 10):** beyond the number of independent keys (10 `NODE_*`), concurrent txns targeting the *same* key within one block fail validation with `MVCC_READ_CONFLICT` (50% fail @ conc 20, 70% @ conc 40). Goodput therefore peaks when concurrency ≈ the number of conflict-free keys — a real, transferable property of Fabric's optimistic-concurrency (read-set/write-set) validation, not a tuning artefact.

## Honest scope

- Single-host test-network (2 orgs); not a geo-distributed multi-bank deployment. Absolute tps is hardware/− and BatchTimeout-bound, so the *shape* (batching amortises the timeout) is the transferable result, not the constant.
- Consensus itself is **stock Fabric Raft**; our contribution is the RL-governed leader-selection + incentive layer running on top, now reporting these **measured** numbers (`leader_block.py`, `use_measured_consensus=True`).
